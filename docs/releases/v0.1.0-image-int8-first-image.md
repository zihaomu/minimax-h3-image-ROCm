# v0.1.0-image-int8-first-image

Frozen on 2026-11-13. This tag preserves the first complete MiniMax-H3-Image INT8 text-to-image request on one Radeon AI PRO R9700: **2048×2048, six steps, CFG=1, and a workflow time of 17.642 seconds**.

Measurements come from the completed `p2-first-image-2048-r2` run. This was one instrumented functional observation. Unprofiled warm-request performance, throughput, reproducibility, TP2, four-GPU execution, 4K, and original BF16 precision were not qualified by this release. No GPU benchmark was rerun during publication.

This English translation on `main` preserves the historical measurements and validation scope. Report hashes in the frozen manifest refer to the original report files at [tag `v0.1.0-image-int8-first-image`](https://github.com/zihaomu/minimax-h3-image-ROCm/tree/v0.1.0-image-int8-first-image). The tag and its original files are unchanged.

## Timing and memory

| Metric | Single observed request |
|---|---:|
| Full workflow request | **17.641758 s** |
| Text conditioning, including stage loading | 5.273793 s |
| KSampler, including loading and diagnostics | 9.293759 s |
| VAE decode, including stage loading | 1.673192 s |
| PNG save node | 0.497275 s |
| Sampled whole-card VRAM peak | 31.618 GiB |
| Peak process RSS | 2.857 GiB |

Full-request timing starts at the executor call and ends after image saving and GPU synchronization. It excludes container and application startup. The request includes synchronization at node boundaries, tensor saving, dispatch counting, and CPU profiling of the first SDPA call in relevant nodes. Stage times include this instrumentation and are not pure kernel times; they cannot simply be added to obtain full-request time.

There was only one successful sample, so no warm-request median or concurrent-throughput statistics are available. An earlier interrupted attempt affected filesystem caches, so the result does not establish cold-storage latency. Whole-card VRAM was sampled approximately every two seconds, with an observed peak of 33,949,990,912 bytes. Torch allocator statistics do not cover all DynamicVRAM weight allocations.

## Validation scope and reproduction

The original request completed normally and retained six-step records and a 2048×2048 PNG. Saved tensors passed finite-value checks, and visual inspection found no blank or corrupted image. Output PNG SHA256:

```text
83b075e1aa8deca8bc8e8fed4f08d3b0bc078fde91617370282ed12d5e9d9c3f
```

At release, full-input A/A, multiple prompts/seeds, unprofiled warm requests, editing, comparison against original BF16 weights, and multi-GPU validation remained pending for this baseline. A first image does not establish general image quality or lossless quantization, or guarantee identical latency or PNG bytes in another environment.

In a workspace with the shared ROCm 10.1 foundation, pinned dependencies, and the model files above already prepared, check out the tag and use a new run directory. Set `SETUP_GPU_ID` to an available physical GPU ID on your machine:

```bash
git fetch origin tag v0.1.0-image-int8-first-image
git switch --detach v0.1.0-image-int8-first-image
python3 tools/run_rocm10.py --gpu "${SETUP_GPU_ID:?Set SETUP_GPU_ID to an available physical GPU ID}" --run-dir runs/reproduce-v0.1.0-image-int8-first-image -- .runtime/venv/bin/python tools/run_image.py
```

Execution must pass the launcher's shared-reservation, device-ownership, and allowed-device checks. See [QUICKSTART](../QUICKSTART.md) for prerequisites. The public release contains source, configuration, and prepared documentation. Local `vibe/`, `research/`, weights, environments, raw tensors, images, and run logs remain outside Git.
